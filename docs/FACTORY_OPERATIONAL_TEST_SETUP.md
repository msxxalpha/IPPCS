# راه‌اندازی IPPCS برای آزمون عملیاتی کنترل‌شده روی IIS

**دامنه:** فقط محیط UAT کارخانه با دیتابیس مستقل IPPCS و داده‌های آزمایشی/واقعیِ مجاز. این راهنما مجوز بهره‌برداری رسمی یا Merge با `main` نیست.

## وضعیت پیش‌نیاز

از Stage 63، میزبان ASP.NET Core در محیط غیر Development می‌تواند اجرا شود. احراز هویت محلی Identity، نقش‌ها، محدودیت تلاش ورود، CSRF و کنترل دسترسی API فعال می‌مانند؛ Swagger در Production فعال نیست، HSTS اعمال می‌شود و کوکی احراز هویت فقط روی HTTPS ارسال می‌شود.

## ۱) جداسازی محیط آزمون

- یک VM یا Windows Server و IIS مجزا یا یک سایت IIS مستقل برای UAT انتخاب کنید.
- یک دیتابیس جدید با نامی مانند `IPPCS_UAT` روی SQL Server آزمایشی بسازید؛ از بانک‌های ERP/انبار/خرید/فروش/منابع انسانی استفاده نکنید.
- قبل از هر ارتقا Backup بگیرید. Migration را روی دیتابیس موجود بدون بررسی و نسخه پشتیبان اجرا نکنید.
- هیچ حساب یا رمز پیش‌فرضی در برنامه وجود ندارد. رمزها را فقط در Secret Store/Environment امن سرور نگه دارید.

## ۲) ساخت و اجرای نصب‌کننده SQL

روی ماشین توسعه با .NET SDK 10، ابزار `dotnet-ef 10` و Python 3:

```powershell
dotnet tool install --global dotnet-ef --version 10.0.0
powershell -ExecutionPolicy Bypass -File .\scripts\Export-IPPCSDatabaseSql.ps1 -Database IPPCS_UAT
```

فایل `database/IPPCS_UAT_Complete_Install.sql` تولید می‌شود؛ این فرمان به SQL Server وصل نمی‌شود و SQL را اجرا نمی‌کند. فایل را بازبینی کنید، سپس روی SQL Server UAT خالی از طریق SSMS اجرا کنید. قبل از اجرا نام دیتابیس مقصد را کنترل کنید. پس از اجرا وجود `AspNetUsers`، `ManufacturingOrders` و `__EFMigrationsHistory` را بررسی کنید.

برای هویت App Pool فقط مجوزهای لازم روی همین دیتابیس IPPCS_UAT بدهید. از sysadmin یا db_owner دائمی برای حساب برنامه استفاده نکنید؛ در نصب/ارتقا، حساب DBA جداگانه Migrationها را اعمال کند.

## ۳) انتشار وب روی IIS

- IIS و **.NET 10 Hosting Bundle** سازگار نصب باشند؛ پس از نصب Hosting Bundle، IIS را طبق رویه سازمان Restart کنید.
- خروجی Release را روی ماشین Build تولید کنید:

```powershell
dotnet publish .\src\IPPCS.Web\IPPCS.Web.csproj -c Release -o .\publish\IPPCS
```

- خروجی را به پوشه سایت UAT کپی کنید. Application Pool را روی **No Managed Code** و هویت اختصاصی کم‌دسترسی تنظیم کنید.
- Binding فقط HTTPS با گواهی معتبر سازمانی داشته باشد. دسترسی HTTP را صرفاً برای Redirect نگه دارید؛ پورت برنامه را مستقیماً در شبکه کارخانه منتشر نکنید.
- در تنظیمات امن محیط برنامه این مقادیر را تعریف کنید (نه در Git یا appsettings.json):

| متغیر محیطی | مقدار |
|---|---|
| `ASPNETCORE_ENVIRONMENT` | `Production` |
| `ConnectionStrings__Production` | اتصال اختصاصی به `IPPCS_UAT` با هویت App Pool یا SQL login محدود |
| `Bootstrap__EnableInitialAdmin` | فقط برای اولین راه‌اندازی `true` |
| `Bootstrap__AdminUsername` | نام مدیر UAT مورد تأیید |
| `Bootstrap__AdminPassword` | رمز قوی و یکتا مطابق سیاست ۱۲ نویسه و پیچیدگی |

برای جلوگیری از باقی‌ماندن راز در فایل‌های قابل خواندن، مقادیر محرمانه را از Secret Store سازمان یا متغیرهای محیطی امن ماشین/App Pool تأمین کنید. از قراردادن رمز در خط فرمان قابل ثبت، Git، فایل منتشرشده یا گزارش پشتیبانی خودداری کنید.

## ۴) ساخت مدیر اولیه به‌صورت یک‌باره

1. دیتابیس باید همه Migrationهای Commit‌شده را داشته باشد.
2. متغیرهای Bootstrap را فقط برای اولین Start فعال کنید.
3. سرویس در صورت نبود مدیر، نقش Administrator و حساب مشخص‌شده را ایجاد می‌کند؛ اگر مدیر از قبل وجود داشته باشد، حساب دیگری را ارتقا نمی‌دهد.
4. پس از ورود موفق و کنترل `/auth/me`، فوراً `Bootstrap__EnableInitialAdmin` و مقادیر Bootstrap را از محیط حذف کنید و سایت را Restart کنید.
5. سپس حساب‌های Planner، ProductionOperator و QualityInspector را از صفحه مدیریت کاربران، با تفکیک وظایف و اصل حداقل دسترسی ایجاد کنید.

اگر Bootstrap در زمان دیتابیس ناقص اجرا شود، برنامه مدیر نمی‌سازد؛ Migrationها را کامل و سپس با تنظیمات امن دوباره راه‌اندازی کنید.

## ۵) آزمون سلامت و مسیر عملیاتی

- `/health` باید `status=ready` و نسخه جاری را نشان دهد. این فقط سلامت اتصال و Migrationها را ثابت می‌کند.
- `/login.html` باید فقط روی HTTPS در دسترس باشد؛ کوکی `IPPCS.Auth` باید HttpOnly، SameSite=Strict و Secure باشد.
- `/swagger` در Production نباید در دسترس باشد.
- صفحه `/factory-release-readiness.html` را بازبینی کنید؛ تعداد ماژول‌های Factory Accepted باید صفر بماند تا پذیرش رسمی انجام شود.
- سناریوی کامل را مطابق `docs/FIRST_UAT_TEST_PACK.md` اجرا کنید: اطلاعات پایه، Routing و BOM مصوب، MPS، کنترل پلن، آزادسازی دستور، ثبت عملیات، کیفیت، مصرف مواد، شجره، گزارش و بازیابی.
- برای هر عملیات واقعی، شماره سفارش/بچ با پیشوند `UAT-` و مجوز کتبی مسئول کارخانه داشته باشید. ابتدا یک محصول/خط محدود و یک شیفت را انتخاب کنید.

## محدودیت‌های مهم نسخه آزمون

این انتشار فقط مسیرهای داخلی IPPCS را آزمایش می‌کند. مصرف مواد، موجودی برنامه‌ریزی، دریافت‌های مورد انتظار، بهای تبدیل و ظرفیت‌ها مستقل و دستی‌اند؛ هیچ حرکت فیزیکی انبار، خرید، فروش، منابع انسانی، حسابداری، PLC یا اتصال ERP انجام نمی‌شود. خروجی MRP/APS پیش‌نمایش برنامه‌ریزی است، نه مجوز آزادسازی خودکار یا تعهد قطعی مواد. اصلاح/برگشت برخی ثبت‌های خط، شیفت‌های پیچیده، تأیید نهایی KPI، پشتیبان‌گیری/بازیابی و آزمون بار/امنیت باید پیش از بهره‌برداری رسمی جداگانه تأیید شوند.

**معیار شروع UAT:** CI کامل روی همان Commit سبز، نصب SQL روی دیتابیس خالی، استقرار IIS با HTTPS، ورود نقش‌محور، عبور سناریوی end-to-end و ثبت صورتجلسه نتایج کاربران کارخانه. تا آن زمان وضعیت سامانه Development/UAT است و نه Production-approved.
